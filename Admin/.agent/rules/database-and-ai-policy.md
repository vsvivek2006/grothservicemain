## 4. AI Content Disclosure Policy (do not deviate)

- AI-generated posts are **never labeled as AI-written anywhere public** — no badge, no disclaimer, no note in the byline, no meta tag.
- Public bylines always use normal author names (e.g. "Growth Service Team"), regardless of how a post was created.
- Internally, store a `source` field per post (`manual` | `ai` | `ai-edited`) for the owner's own tracking only. This field must:
  - Show only in the admin dashboard
  - Never be exposed via any public API response, page source, RSS feed, or sitemap
- **AI-generated content always saves as `status = 'draft'` first.** Nothing generated by AI may be auto-published — a human must open it and explicitly click Publish.
- Before shipping, check that no AI-tool metadata/fingerprints leak into exported HTML (some editors or export libraries inject generator tags — strip these if present).

## 5. Database Schema (Supabase / Postgres)

```sql
create extension if not exists "pgcrypto";

create type post_status as enum ('draft', 'published');
create type post_source as enum ('manual', 'ai', 'ai-edited');

create table posts (
  id uuid primary key default gen_random_uuid(),
  title text not null,
  slug text not null unique,
  content text not null default '',
  meta_description text,
  cover_image_url text,
  author text not null default 'Growth Service Team',
  tags text[] not null default '{}',
  status post_status not null default 'draft',
  source post_source not null default 'manual',
  published_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create index posts_status_idx on posts (status);
create index posts_published_at_idx on posts (published_at desc);

-- Row Level Security
alter table posts enable row level security;

-- Public (anon) can only read published posts
create policy "Public can read published posts"
  on posts for select
  using (status = 'published');

-- Any authenticated Supabase user has full access.
-- Assumption: the ONLY Supabase Auth accounts in this project belong to
-- trusted admins — there is no public sign-up flow. If that ever changes,
-- this policy must be tightened (e.g. custom role/claim check).
create policy "Authenticated admins have full access"
  on posts for all
  using (auth.role() = 'authenticated')
  with check (auth.role() = 'authenticated');
```

Even though RLS restricts row access, be deliberate about which **columns** are selected on public pages too — use explicit column lists (`select id, title, slug, content, ...`), never `select *`, so `source` and any future internal-only field can't leak by accident.

## 9. API Contract Reference

**POST `/api/admin/blog/generate`** — must verify an authenticated admin session server-side before calling the AI provider.

Request:
```json
{
  "topic": "Local SEO tips for small businesses in India",
  "tone": "professional",
  "keywords": ["local SEO", "Google My Business"],
  "wordCount": 900,
  "audience": "small business owners"
}
```

Response:
```json
{
  "title": "5 Local SEO Tips Every Small Business in India Needs",
  "metaDescription": "...",
  "content": "<h2>...</h2><p>...</p>",
  "suggestedTags": ["Local SEO", "Small Business", "Google My Business"]
}
```

On failure, return a clear error message the UI can toast — never let the admin page hang silently.
